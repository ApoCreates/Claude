# Portal — منصة إدارة هدر التموين

بروتوتايب ويب كامل لإدارة هدر التموين وسلاسل الإمداد في الفعاليات، بواجهة عربية RTL بالكامل.
**يعمل بدون باك-إند، وبدون أي مفتاح API، وبدون أي اتصال خارجي وقت التشغيل.**

---

## التشغيل

ثلاث طرق، كلها بلا تثبيت أي اعتمادية:

```bash
# 1) افتح الملف مباشرة
open index.html          # أو انقر عليه نقراً مزدوجاً

# 2) أو شغّل خادماً محلياً (وحدة http المدمجة في Node — لا npm install)
npm run dev              # http://localhost:5173

# 3) أو ابنِ نسخة بملف واحد للمشاركة/الاستضافة
npm run build:artifact   # dist/portal-artifact.html
```

### نسخة الملف الواحد

`npm run build:artifact` يجمع الـ CSS وكل وحدات الـ JS في صفحة واحدة مكتفية ذاتياً
(بلا وسوم `html/head/body` خارجية، واتجاه RTL يُضبط على عنصر الجذر برمجياً) لتصلح
للاستضافة في بيئات تقدّم صفحة واحدة فقط. الوظائف كاملة في النسختين؛ الفرق الوحيد أن
التصدير يستخدم مسار الحفظ لدى المضيف حين يوفّره، ويسقط إلى رابط blob محلياً — مع
«نسخ إلى الحافظة» كمسار يعمل في كل الحالات.

لا يوجد `node_modules`، ولا خطوة بناء، ولا CDN. كل ملفات JS/CSS محلية، والخط عربي من النظام
(`Cairo` → `IBM Plex Sans Arabic` → `Noto Sans Arabic` → `Dubai` → احتياطي النظام).

## الشاشات الست

| الشاشة | ما تقدمه |
|--------|----------|
| **لوحة القيادة** | ست بطاقات KPI + الهدر والكلفة حسب الفئات الست + الهدر عبر الزمن بخط اتجاه + توزيع الخطورة + التوزيع حسب الإمارة والمزود. **كل رقم يُحسب حياً من البيانات — لا شيء مثبَّت.** |
| **سجل الفعاليات** | جدول قابل للفرز على ستة أعمدة، وتصفية بالبحث الحر والفئة والخطورة والإمارة والمزود وحالة الحل. الشارات: ذهبي `golden_approved` · أزرق `generated` · رمادي «بلا حل». |
| **تفاصيل الفعالية** | كل الحقول الكمية والوصفية + المشكلات الفرعية + السرد + الحل ببنيته الكاملة + **أثر المحرك** (لماذا اختار ما اختار) ومصفوفة الخطورة بمحاورها الثلاثة. |
| **توليد الحل** | زر «⚡ ولّد الحل» لأي فعالية بلا حل ← نافذة مراجعة ← حفظ كـ `generated` أو تعديل ثم اعتماد كـ `golden_approved`. |
| **إضافة فعالية** | نموذج بنفس مخطط JSON (كل الحقول + مشكلات فرعية متعددة)، بتحقق كامل ورسائل خطأ عربية، ومعاينة حية لنسبة الهدر والكلفة — أو **ورقة Excel** تُملأ خارج المنصة وتُرفع. |
| **منطق المنصة** | عرض منسق لـ `portal_logic.md`: الفئات الست بكلماتها، مصفوفة الخطورة، أنماط الفشل الأربعة، بنية الحل الإلزامية، الوحدات الأربع، الأمثلة الذهبية، وقواعد المحرك. |

## المحرك الحتمي (`assets/rule-engine.js`)

`portal_logic.md` ليس نصاً معروضاً فقط — هو مُنفَّذ. المحرك يمر بالتسلسل نفسه في القسم 8،
**بلا نموذج لغوي وبلا عشوائية: نفس المدخل يعطي نفس المخرَج حرفياً في كل مرة.**

1. **التصنيف** — مطابقة موزونة لكلمات الفئات الست على `supply_chain_issue` و`receiving_intake_issue`
   (وزن مضاعف للكلمات الأصلية في الوثيقة)، ثم `root_cause` فالسرد، مع إشارة من فئات المشكلات الفرعية.
2. **نمط الفشل** — مؤشرات نصية موزونة للأنماط الأربعة، مع نمط افتراضي لكل فئة عند التعادل.
3. **الخطورة** — أعلى المحاور الثلاثة (مالي/سلامة/سمعة)، **لا متوسطها**، مع بيان المحور الحاكم.
4. **القالب** — أقرب مثال ذهبي: نفس الفئة (+10) ثم نفس نمط الفشل (+6) ثم نفس الوحدة (+3).
   وعند وجود طبقة ثانية مصرَّح بها في `incidents` يغطيها مثال ذهبي آخر، يُسحب **قالب مزج**.
5. **التخصيص** — قواعد موضوع مقيّدة بالفئة (19 قاعدة: منصات، جمارك، مصاعد، مولدات، صلاحية، تسجيل،
   طقس، توزيع ديناميكي، تغيير قائمة، فرز، تبرع…) تُحقن باسم الفعالية وموقعها ومزودها وكمياتها.
   لا نسخ حرفي — يتحقق `npm test` من ذلك صراحةً.
6. **المخرَج** — بنفس مخطط `golden_solution` حرفياً بحالة `generated`؛ الاعتماد اليدوي يحوّله إلى
   `golden_approved` فيصبح متاحاً للمحرك كقالب.

أثر التنفيذ (`RuleEngine.explain`) يُحسب حياً للعرض ولا يُحفظ داخل الحل، حفاظاً على نقاء المخطط.

### معايير القبول المتحققة في `npm test`

| الحالة | المتوقع | النتيجة |
|--------|---------|---------|
| EV-008 تعطل مولد التبريد | منطق قريب من EV-001 | قالب **EV-001**، نمط «نقطة فشل واحدة»، وحدة مراقبة سلسلة التبريد |
| EV-019 المؤتمر الهجين | منطق قريب من EV-010 | قالب **EV-010**، نمط «قرار مبكر غير قابل للتصحيح» |
| EV-002 فائض الزفاف | يمزج EV-010 وEV-020 | قالب **EV-010** + مزج **EV-020**: معامل تحويل الحضور + مذكرة تفاهم للتبرع |

## البيانات

- البذرة مدمجة في `assets/data.js` (مولَّدة من `data/catering_incidents_dataset.json` عبر
  `npm run build:data` — الملفان متطابقان حرفياً).
- عند أول تشغيل تُنسخ إلى `localStorage` تحت المفتاح `portal.catering.dataset.v1`،
  وتصبح هي مصدر الحقيقة القابل للتعديل. تحديث الصفحة لا يفقد شيئاً.
- **تصدير**: ملف JSON بنفس المخطط الأصلي حرفياً، مع تحديث `events_count` و`golden_examples` تلقائياً.
- **استيراد**: يقبل `.xlsx` و`.csv` و`.json`. تحقق كامل قبل أي كتابة (مخطط، معرّفات مكررة،
  متلف > مورد)، معاينة لما سيُستورد، ثم اختيار **دمج** أو **استبدال** بتأكيد صريح.
  الملف غير الصالح يُرفض بالكامل ولا يُكتب منه شيء.
- **إعادة تعيين**: تُرجع البيانات الأصلية العشرين وأمثلتها الذهبية الأربعة (بتأكيد).

## ورقة التعبئة (Excel) — بلا JSON وبلا API

زر **«ورقة التعبئة»** ينزّل ملف `.xlsx` حقيقياً يفتح في Excel وNumbers وGoogle Sheets،
فيه ثلاث أوراق:

| الورقة | ماذا تحوي |
|---|---|
| **الفعاليات** | 21 عموداً، كل عمود **سؤال بالعربية** («ما السبب الجذري؟»، «الطعام المتلف (كغ)») وتحته سطر تلميح ومثال ملوّن. |
| **المشكلات الفرعية** | صف لكل طبقة فشل، مربوط بمعرّف الفعالية. |
| **التعليمات** | خطوات التعبئة، القواعد التي يجب أن تتحقق، الفئات الست منسوخة حرفياً، وشرح كيف تُحسب الخطورة. |

المستخدم لا يحسب شيئاً: **نسبة الهدر، وكلفة الهدر، وفرق الحضور، ودرجة الخطورة** تُشتق
كلها من الأرقام المدخلة عند الرفع. ومن ترك عمود النقل أو الاستلام بعبارة «لا مشكلة»
لا يُسحب تصنيفه نحو طبقة لم يحدث فيها شيء.

عند الرفع تعرض المنصة **معاينة** بما قُرئ (المعرّف، الفعالية، الهدر، الكلفة، الخطورة
المحسوبة) وقائمة بالأخطاء المانعة قبل أن تكتب أي شيء، ثم تصنّف كل فعالية وتولّد لها
حلاً بالمحرك الحتمي نفسه.

**كل ذلك داخل المتصفح.** `assets/xlsx.js` يكتب ملف xlsx (ZIP مخزَّن + CRC32 + XML)
ويقرأه (مسح EOCD ← الدليل المركزي ← فك ضغط `DecompressionStream('deflate-raw')`)،
مع دعم `sharedStrings` وخلايا `inlineStr` — أي أن ما يخرج من Excel نفسه يُقرأ كما هو.
لا مكتبة، لا خادم، لا مفتاح. ومن يفضّل صيغة أبسط يجد زر **نسخة CSV** بجانبه.

### ملاحظة على فروقات الخطورة

المحرك يعيد إنتاج الخطورة المسجّلة يدوياً في **18 من 20** فعالية. الفارقان مقصودان ومعروضان في
الواجهة داخل «أثر المحرك»، ولا تُعدَّل بهما البيانات تلقائياً:

- **EV-007**: المصفوفة تعطي «عالية» لأن الأثر يذكر غرامة تعاقدية (25,000 د.إ) — ومحور
  السمعة/التعاقد يصنّف «غرامة أو ملاحظة رسمية» عاليةً. السجل اليدوي يقول «متوسطة».
- **EV-019**: المصفوفة تعطي «متوسطة» (كلفة 8,960 د.إ، بلا مؤشر سلامة أو سمعة). السجل اليدوي يقول
  «عالية» استناداً إلى نسبة هدر 53.8% — وهو بُعد لا تحمله المحاور الثلاثة في الوثيقة.

في كلتا الحالتين تعرض المنصة الخطورتين معاً مع المحور الحاكم، وتترك القرار للمراجع البشري.

## ملاحظات تقنية

- الوحدات تُحمَّل كـ classic scripts لا ES modules، ليعمل الفتح المباشر عبر `file://` دون قيود CORS.
- الرسوم SVG مرسومة يدوياً: أعمدة أفقية للتسميات العربية، سلسلة زمنية بخط اتجاه، وحلقة توزيع —
  كلها تُقرأ من اليمين لليسار مع `direction="rtl"` صريح على النصوص لمنع تداخل التسميات.
- متجاوب حتى عرض 390px بلا أي تجاوز أفقي (الجداول العريضة تنزلق داخل حاويتها فقط).
- كل مدخلات المستخدم تمر عبر تهريب HTML قبل العرض.
- عند تعذّر `localStorage` (وضع خاص) يعمل البروتوتايب بالكامل مع تنبيه بأن التعديلات لن تبقى.
